# QA 收集表 → 病-药-效 映射逻辑

伙伴填写的《伙伴QA收集表》是本 skill 的主要输入。表分两大区块：**联合方案区（12字段）** 和 **客户案例区（12字段）**。下面是每个字段如何映射到病-药-效底座。

## 一、QA 表三种填写情况（先判断）

- **情况1**：有联合方案 + 带授权客户案例 → 两区都填 → "效"可用真实客户名+数据
- **情况2**：有联合方案 + 无/未授权案例 → 只填联合方案区 → "效"脱敏抽象成广义客户价值
- **情况3**：只有单个客户案例 → 只填客户案例区 → 围绕该客户讲病药效

---

## 二、联合方案区字段映射

| QA 字段 | 映射到 | 用法 |
|---|---|---|
| 方案名称 | 标识 | 方案名 + 一句 slogan，用于封面/Key Message 提炼 |
| 方案服务的业务场景 | 病(背景) | 界定客户是谁、在什么场景遇到问题 |
| 方案服务的客群 | 受众定位 | 决定语言/价值点面向谁（如 CFO/CIO 决策层）|
| **方案针对的业务痛点** | **病** | 直接映射"病"，逐条转成客户视角痛点 |
| 涉及腾讯云解决方案 | 药 | 腾讯云侧提供的方案能力 |
| 涉及腾讯云产品 | 药(支撑) | 技术支撑，**仅作"药"的底层说明，不进"效"** |
| 伙伴在方案中的角色 | 药(1+1>2) | 伙伴做什么 → 与腾讯云互补的协同点 |
| 方案整体架构 | 药(结构) | 方案怎么搭起来的（如三层架构）|
| **方案整体价值** | **效(定性)** | 能力/改变叙述："变得怎样了"（如"报表秒级归集""一穿到底"）|
| **方案差异化价值** | 药/效(竞争) | "你有我没有"——对标竞品、只有腾讯云×伙伴能给的价值 |
| **方案效益** | **效(定量)** | 整体价值的**可量化版**："提升了多少"（百分比/倍数/时间对比）|
| 是否有落地客户案例 | 模式开关 | 决定走"有授权"还是"脱敏"写法 |

### 字段释义澄清（填表/解析时的关键区分）

**「方案整体价值」 vs 「方案效益」**
- 整体价值 = **能力叙述**（定性，形容词/能力项）→ "报表秒级归集""一穿到底可追溯"
- 效益 = **数据佐证**（定量）→ "采集效率+90%""周期数周→分钟级"
- 一句话：**效益是整体价值的"可量化版本"**。

**「方案差异化价值」**
- 主打"**你有我没有**"：对标竞品（如其他云厂商同类方案），点出**只有腾讯云×本伙伴能提供、竞品给不了**的价值点。
- 不是罗列所有价值，而是筛出"独一份"的那几条。

## 三、客户案例区字段映射

| QA 字段 | 映射到 | 用法 |
|---|---|---|
| 客户名称（可脱敏） | 标识 | 授权→用真名；未授权→"某类客户" |
| 客户所在国家/地区 | 病(背景) | 场景背景 |
| 客户目标出海国家/地区 | 病(背景) | 出海方向 |
| **客户业务场景** | 病(背景) | 客户是谁、做什么 |
| **客户业务痛点** | **病** | 直接映射"病" |
| 客户采购的解决方案 | 药 | 客户买了什么方案 |
| 解决方案涉及的腾讯云产品 | 药(支撑) | 技术支撑，不进"效" |
| **解决方案整体价值** | 药/效(供给侧) | **方案端提供的能力**（"方案能……"）|
| 伙伴在该案例中提供的服务 | 药(1+1>2) | 伙伴做的事 |
| **客户收益** | **效(结果侧)** | **该客户实际拿到的结果**（"客户得到了……"，带量化数据）|
| 客户案例最大传播价值点 | Key Message | 直接提炼二创视频的钩子/Key Message |
| 一句话为什么选择腾讯云 | 药/背书 | 收口句、信任状 |

### 字段释义澄清

**「解决方案整体价值」 vs 「客户收益」**
- 解决方案整体价值 = **方案本身提供的能力**（供给侧，还没落到这个客户）→ "云直播提供超低延迟、高并发、全球节点"
- 客户收益 = **这个客户实际拿到的结果**（结果侧）→ "PB Tech 首场2小时GMV近400万、延迟<1秒"
- 一句话：**整体价值=方案端能力（供给侧），客户收益=客户端实得（结果侧）**。

### 实战范例：PB Tech 客户案例「解决方案整体价值」（供给侧能力，锚定架构师原话）

> 场景：CSS 云直播、侧重快直播 LEB。写"整体价值"时只讲**方案能力**，把 <1秒/GMV400万/省76% 这些**结果侧数据留给「客户收益」**，两栏不串场。

正解（3条，全部锚定架构师原话，不生造词）：
1. **超低延迟实时互动**：快直播 LEB 基于 WebRTC 技术，端到端延迟做到 1 秒以内，观众提问主播几乎能实时看到、实时回答，支撑直播带货的实时互动。
2. **画质自适应、全球流畅观看**：自适应码率让画质随网络智能调节——网好看高清、网弱不卡顿，叠加腾讯云全球 CDN 节点，保障海外观众随时随地流畅观看。
3. **极速高清转码、显著降本**：腾讯云自研极速高清转码技术（TSC），在主观画质不变的前提下压缩超 70% 码率，帮客户大幅降低带宽与存储成本，观众也能用更少流量看高清画面。

要点：① 主语宾语补全，不用"采集到分发""集成简"等费解简写；② 带宽用架构师口径"超 70%"，实测"76%"归客户收益；③ 供给侧只讲"方案能提供什么能力"。

## 四、解析时的注意事项

1. **产品字段只进"药"不进"效"**：腾讯云产品清单（GAAP/WAF/CSS等）是技术支撑，讲"药"时点到，讲"效"时必须翻译成业务价值。
2. **痛点逐条转客户视角**：QA 里的痛点可能偏中性描述，解析时转成"客户会痛在哪、慌在哪"。
3. **缺"风险"字段**：QA 表通常没有独立"风险"字段，需从"业务痛点"合理推演代价，并标注"建议与伙伴确认"。
4. **示例列（简略示例）只是参考**：伙伴填的是"待填写"列；解析真实项目时以待填写列为准，示例列用于理解字段意图。
5. **发现填写串场要提示**：如客户案例的"整体价值"填成了别的方案价值（复制粘贴错），解析时提示用户核对。
6. **"效"里的数据分清目标值vs实测值（悦智赛马会教训）**：「客户收益」字段里可能混着"方案设定的目标"（如"RAG 准确率对标 90%"）和"已达成的实测结果"。解析授权案例时，把明显是**目标值**的数据标出来，产出后提示用户对外发布前核实是否已达成实测口径。
7. **单个 QA sheet 即可跑通全流程**：悦智赛马会验证——一个填写完整的 QA sheet（含痛点/腾讯云能力/伙伴角色/三层架构/价值/效益/客户收益/最大传播点）足以支撑 PPT 故事线 + 二创视频叙事线两个交付物，无需额外素材。
8. **QA 字段是骨架，业务血肉靠主动检索补**（约束五）：QA 里「客户业务场景」「客户业务痛点」往往只有一句话，解析后应**主动上网检索**补场景血肉——**具体案例具体查**（这次伙伴是谁就查谁的官网，客户是谁就查谁的官网，不套用任何默认官网）：
   - 查 **该客户的官网**：客户体量、客群构成、服务范围，理解"这个痛点为什么致命"。
   - 查 **该伙伴的官网**的方案/客户案例页：看该联合方案是否已 publish 官方介绍，补 know-how、印证 QA 口径。
   - **冲突时以 QA list 为准**（一手 > 二手）；网络补充无法印证的，产出时标注"（网络补充，待伙伴确认）"。写进产出物的网络内容要**附信源链接**（像论文引用）。
9. **痛点/能力字段多是"供应商功能语"，映射到叙事必须翻译**（约束六-C/F）：QA 里填的"重复咨询量大""知识散落各处""需支持多语言"是供应商视角功能罗列，映射到"病"时**必须过翻译公式**（功能语→客户后果→business损失），落到会让企业痛的利益点；映射到"药"时把散乱能力点**重组成分层架构**，别照抄上屏。

10. **「解决方案涉及的腾讯云产品」字段 → 必须去腾讯云产品官网查实，再落笔**（约束五第③类锚点 / 约束六-F）：这个字段是理解"腾讯云在本方案里到底带来什么价值"的钥匙。QA 里往往只填了产品名（如 ADP、Desk、CVM），**光有产品名写不出价值**，必须：
    - **QA 填了什么产品，就查什么产品的官网**（不套用任何默认产品清单）。示例锚点：ADP=`https://cloud.tencent.com/product/adp`（Agentic RAG 检索引擎 + Workflow 编排 + 内容审核敏感拦截）、Desk=`https://cloud.tencent.com/document/product/269/96056`（融合 LLM+NLP、关联上下文多轮、全渠道 H5/小程序接入、转人工不丢对话）。
    - 查清后要**把产品能力翻译成"这个方案里的具体价值"再写进产出物**——不是罗列官网功能，而是回答"因为用了这个产品，客户能得到什么别处得不到的东西"。检索到的一切都要**体现在内容撰写的笔力上**，不能只作为背景理解。
    - 腾讯云产品能力是"药"的技术底座，与伙伴的定制交付构成 **1+1>2**（腾讯云做产品/技术底座 × 伙伴做行业定制与交付），产出时讲清双方各自价值。

# 联合方案 & 二创视频 故事线撰写

> 🚨 **最高原则｜demo ≠ default（务必牢记）**
> 本 skill 的一切规则、模板、字段都是**通用**的。真实使用场景是：**每次用户在提示词里扔进一份新伙伴的 QA list**（里面含该伙伴自己的联合方案 case / 客户案例 case），本 skill 据此产出。
> - **绝不把任何具体伙伴（如悦智）、任何具体客户（如香港赛马会）、任何具体行业设成默认值。** 它们只是**测试过 skill 的 demo case**。
> - 文中出现的悦智 / 香港赛马会 / 信永中和 / PB Tech / 金川等，**一律是"脱敏举例（示例，非默认）"**，用于说明方法，不代表下次任务的对象。
> - 所有官网锚点（yuezhi.ai、hkjc.com 等）都是**举例**——真实检索要**具体案例具体分析**：这次伙伴是谁就查谁的官网，这次客户是谁就查谁的官网。

> 💡 **使用前置提醒（每次触发本 skill 都要在开头提醒用户）**：
> 1. **建议开启「内容创作专家」角色**——本 skill 输出的是市场营销文案，内容创作专家的笔力和营销语感效果更好。
> 2. **善用 Google 侧边栏 Gemini 做检索**——那里是**上下文一手的地方**，可以直接分享/引用当前打开的网页标签页（伙伴官网、客户官网、腾讯云产品页），无需单独上传 context，检索出的内容效果也更好。做主动检索（约束五三类锚点）时优先用它。

## 这个 Skill 是什么

腾讯云生态联合方案的**内容策划脑**。服务两个前后衔接的产出物，二者**同根同调**：

1. **联合方案 PPT 故事线**（完整版）——逐页要点 + 每页背后的策划逻辑
2. **二创短视频叙事线**（~1.5分钟社媒轻传播版）——逐幕口播，抽主线、勾兴趣、导流下载完整方案

**只产出文字故事线/框架，不产成品文件（PPT/视频）。** 成品制作交给用户或其他工具。默认只在对话里交付；用户明确说"写进文档/PPT"时才落地成文件。

> 🔖 **交付物的 stage 定位（重要）**：本 skill 产出的文字版 PPT 与视频叙事线**都是"供与伙伴二次讨论的初稿"，不是最终定稿**。
> - 真实流程：`伙伴首轮 QA list → 本 skill 产出初稿 → 拿给伙伴过目 → 双方二次讨论(补充/查漏/纠偏) → 才定稿`。
> - 因此产出要**主动预留"待伙伴确认/补充"的标注**（如推演出来的风险、目标值 vs 实测值、网络补充的 know-how 存疑处），方便二次讨论时聚焦。
> - 交付时**明确告知用户这是讨论初稿**，而非可直接对外发布的成品。

> 📁 **落地文件格式约定（悦智赛马会实操验证）**：当用户明确要文件时——
> - **PPT 故事线** → 写成 **Markdown（.md）**，用标题层级 + 层级词（标题/副标题/描述/总结句）承载"文字版 PPT"结构，交设计师直接读。
> - **二创视频叙事线** → 写成 **Excel（.xlsx）**，固定 5 列表头（视频结构/关键目标/文案结构/文案内容（旁白）/预计时长）。
> - 详见两个 reference 的"产出形态"章节与技术生成经验。

## 背景：什么是「联合解决方案」

腾讯云与**生态型伙伴**（咨询型 / Global ISV / Global MSP / 硬件 / 行业 ISV，**非转售型**）一起，面向共同客户、服务出海场景，做能力互补的联合方案。灵魂是 **1+1>2 的能力协同**（如「咨询+产品+交付」三位一体闭环），但——

> ⚠️ **主轴永远是客户价值，1+1>2 是锦上添花**（对外塑造生态形象，点到即止），不是硬骨架。

不限行业/区域，重点是"能力模型互补的故事"。

### 1+1>2 的准确内涵（别写偏）

- ❌ **不是**"两家都很强""强强联合"这种空泛表述。
- ✅ **是**：腾讯云（技术底座）+ 不同能力模型的伙伴 → 拼出**「一站式、全链路服务闭环」**，让**客户不用自己找多家拼凑，一站到底**。
- 范例：毕马威(咨询) × 腾讯云(技术底座) × 华云中盛(实施) = 咨询+产品+实施的全生命周期一站式交付。**闭环 = 客户免于多方拼凑。**
- ⚠️ 若某个客户案例**无伙伴参与**（如 PB Tech 由腾讯云 CSS 直接服务），**不硬套 1+1>2**，但"一站式全链路打通"的价值感仍可保留。

## 核心叙事逻辑：病-药-效（客户视角贯穿）

```
病（客户业务痛点） → 风险（痛点带来的代价） → 药（腾讯云×伙伴联合方案：怎么解决） → 效（客户拿到的价值/可量化成效）
```

**始终从客户业务视角出发**，不是从技术/产品视角。

## 四条硬约束（每次产出必须执行）

### 约束一：Key Message 统一（先锁一句，再展开）

- **第一步先提炼一句核心 Key Message**，作为整个病-药-效叙事的"北极星"。
- PPT 与视频**都围绕它展开**，并在**头尾反复点题**。
- 要求：① 有行业 know-how；② 理解成本低（目标用户秒 get）；③ 真真实实切中客户痛点。
- 参考样本（信永中和）："合规不再是成本项，而是全球化能力的一部分"。

### 约束二："效"的两种写法（先问案例是否授权）

产出前**先确认**："本次有无可对外授权的客户案例？"

| | 有授权案例 | 无授权案例（如信永中和/金川） |
|---|---|---|
| **"效"怎么写** | 真实客户名 + 可量化数据（如 PB Tech：2小时GMV近400万、延迟<1秒、带宽省76%） | **不出现客户名/金额**，把成效抽象成"**这类客户普遍能得到的业务价值**"（如"数据采集提效90%+、合并报表数周→分钟级、风控从事后→事前"） |
| **视角** | 客户业务视角 | 客户业务视角（同样） |

> 金川案例即典型：有真实成效数据（提效90%+等），但客户不授权 → 联合方案里必须脱敏、抽象成广义客户价值。

> ⚠️ **数据口径校验（悦智赛马会教训）**：即便有授权、可用真名+数据，也要分清数据是**"已达成的实测值"还是"方案设定的目标值"**。QA 表里常混着两者（如"RAG 准确率对标 90%可溯源"其实是目标值，不是已验证实测）。产出后**主动提示用户**："此处 XX 数据看起来是目标值，对外发布前请与伙伴/客户核实是否为已达成实测口径"，避免数据表述偏差引发合规/公关风险。

### 约束三：技术语言 → 客户业务价值（翻译规则）

每一条价值/成效，产出前**自查一遍**：

> **"这句话，客户的老板（CFO/CIO/业务负责人）听得懂、且关心吗？还是只有技术团队才懂的功能罗列？"**

- ❌ 反例（偏技术）："GAP动态路由、WAF防火墙、零信任机制、A-B-C三表架构、13期调整"
- ✅ 正解（客户业务价值）："数据采集效率提升90%""合并报表从数周缩短到分钟级""风险从事后追责变事前预警"

技术词只作为"药"里的支撑说明，**"效"和每页结论句必须翻译成业务价值**。

**判定标尺（真实页面样本，比抽象规则更好用）：**
- ✅ **正面（客户/业务视角）**：如 CSS 云直播功能亮点页——"直播录制 / 直播安全 / 直播转码"，客户一看就懂"我能拿它做什么"。
- 🟡 **偏技术但可接受**：如信永中和产品功能价值页——"并行架构 / A-B-C 表 / 13 期调整"。**能过审、可接受**，因为该海外财务平台**部分底层技术恰是腾讯云提供的**，联合方案刻意强调腾讯云技术贡献是有意为之。**但凡能翻译成业务价值的，优先翻译。**
- 判定口径：技术表述**只在它是"腾讯云贡献点"时**保留；纯为炫技、客户老板听不懂又不关心的，一律翻译成业务价值。

> ⚠️ **"翻译成业务价值 ≠ 为精简造生僻词"**：精简是好的，但不能为压字数造出不常见/费解的搭配，反而抬高理解门槛。
> - ❌ 生造搭配："采集到分发"（采集什么？分发什么？）、"集成简"（什么集成简？）、"直播越做越划算"（不常见搭配）
> - ✅ 正解：**优先复用架构师/业务方的原话**，把主语宾语补全说清楚。如"从采集、传输、转码到分发全链路打通""开发者只需接入 SDK 即可快速开播""在主观画质不变前提下压缩超 70% 码率，降低带宽与存储成本"。
> 一句话：宁可多几个字说清楚，也不为省字造费解词——**理解成本低才是目标，字数少只是手段**。

### 约束四：脱敏检查清单（产出前自查）

- [ ] 未授权客户名是否已隐去？（如"金川集团"→"某大型出海集团"）
- [ ] 具体金额/敏感财务数据是否已脱敏？
- [ ] 是否出现除"腾讯云 / 本次合作伙伴"之外的具体企业名？（行业案例提到的第三方一律隐去）
- [ ] 未授权的产品发布/数据披露是否已规避？

### 约束五：绝不闭门造车——主动检索权威信源补 know-how

**QA list 只是首轮一手素材，不足以支撑高质量叙事。** 拿到 QA list、选定 case 后，**必须主动上网检索**，补充对"联合方案 case"和"客户案例 case"的业务场景理解与行业 know-how。

**信源必须权威（官网优先，杂源慎用）——三类锚点（缺一不可）：**
1. **伙伴官网**的客户案例/解决方案页（举例：`https://www.yuezhi.ai/`，具体案例查具体伙伴）——找该联合方案是否已 publish 的官方介绍，看伙伴在方案里**具体提供了什么能力/交付什么价值**。
2. **客户案例里的客户官网**（举例：`https://www.hkjc.com/zh-hk/index`，具体案例查具体客户）——理解客户真实业务场景、体量、客群、痛点背景。
3. **🔑 方案涉及的腾讯云产品官网**（本轮 mentor 强调，务必执行）——**QA 表「涉及腾讯云产品」字段填了哪些产品，就逐个去腾讯云官网查清它到底是什么、有什么核心能力、能给这个场景带来什么价值**。腾讯云在联合方案里提供的就是"产品/技术"，只有查清产品真本事，才能把"腾讯云带来的价值"写实、写专业，而不是泛泛一句"提供技术底座"。
   - 举例（示例，非默认）：某方案用了 ADP（智能体开发平台 `cloud.tencent.com/product/adp`）+ Desk（在线客服 `cloud.tencent.com/document/product/269/96056`）→ 查出 ADP = Agentic RAG 检索引擎（回答准确可溯源）+ Workflow 多轮编排 + 内容审核/敏感拦截；Desk = 融合 LLM+NLP、关联上下文、多轮任务、全渠道（H5/小程序）接入、转人工不丢对话 → 这些具体能力点才是文案里"腾讯云价值"的血肉。

**检索目的：**
- 把 QA 表里干巴巴的一句话，补出**业务场景的血肉**（客户是谁、多大体量、服务什么人、为什么这个痛点致命）。
- 找到**行业 know-how**，让文案有专业深度、不外行。
- **查清腾讯云产品/伙伴能力的真本事**，让"药"（双方价值）写得具体专业，而非空泛。
- 核对 QA 里提到的方案/数据是否有官方公开佐证。

> ⚠️ **冲突处理铁律：以 QA list 为准。**
> QA list 是伙伴近期**亲自填写的一手资料**；网络信息是**二手资料**，可能过时、不准或张冠李戴。
> 当网络检索结果与 QA list 冲突时，**一律以 QA list 为准**，网络信息仅作背景补充与理解辅助，不覆盖 QA 的事实口径。
> 网络补充的内容若无法与 QA 印证，产出时**标注"（网络补充，待伙伴确认）"**，留到二次讨论核实。

**🧰 推荐工具编排（两个都是「可选增强」，没安装也能用内置工具跑通，不要因为没装就卡住）：**

| 环节 | 推荐工具 | 装了怎么用 | 没装的降级方案 |
|---|---|---|---|
| **前置主动检索**（约束五三类锚点） | `anysearch` skill（可选增强） | 用 `batch_search` 并行查"伙伴官网+客户官网+腾讯云产品官网"三类锚点、用 `extract` 把整页转干净 Markdown、行业数据走垂直域搜索并做时效核对 | 用内置 WebSearch / WebFetch 逐个查，同样能拿到，只是要串行、内容稍杂 |
| **搭「策划案底座」**（Step 1，价值主张/KM/病药效框架） | `brainstorming` skill（可选，仅"极难拆解"时才借） | **只借它的"提问纪律"**（一次只问一个问题、给选择题、关键节点先获批准）做纯发散讨论 | **默认无需外挂**——这套提问纪律已内化进本 skill 的 AI 共创规则；除非底座极难想清才临时借它，且**别让它接管流程走到写技术 spec/代码那步**（那是它的默认终点，与本 skill 场景错配） |

> ⚠️ **数据安全**：anysearch 会把查询词/URL 发到第三方服务。我们查的是**公开官网 + 公开行业数据**，没问题；但 QA 表里若有**未公开的伙伴敏感信息**，那部分**别丢给 anysearch**，改用内置工具或直接读本地文件。

> 📚 **网络信源的引用附录规范（像写论文一样标注来源）**：凡是**从网络检索得到、且写进产出物（叙事线/故事线）的内容**（数据、行业事实、客户背景、行业 know-how），都必须**标注信源**。做法：
> - 在产出物末尾附一个 **「信源附录 / References」** 区块；
> - 逐条列出：`[序号] 引用了什么内容 —— 来源标题 —— URL`；
> - 正文里该处用 `[序号]` 或 `（见附录N）` 呼应。
> - 无权威信源可佐证的数据**不编造**，标注"（待补权威数据源）"。

### 约束六：价值主张 & 痛点，都要落到"客户终局利益"（避免表层化）

这是本 skill 最容易写飘的地方，四条子规则**每次产出前必过**：

**六-A｜价值主张：AI 先判断 + 给理由 + 请用户确认（不锁死选项）**
- 拿到 QA 后，先判断这个方案的核心价值主张更偏哪条线，**常见但不限于**：
  - (A)「降本增效线」——省人力/降成本/提效率；
  - (B)「体验升级 → 收益增长线」——优化客户体验，进而留客/复购/把某职能转化为长期经营价值；
  - (C) 两者都有 / (D) 一条全新的主张（依 QA 实际而定）。
- **做法**：AI 先根据**伙伴填表更强调什么**给出判断 + 理由，**然后停下来请用户确认**（用户可改选、可补充、可给全新主张）。**不要自作主张锁死，也不要硬塞进 A/B 二选一。**
- 无论最终选哪条，都要**往"能帮客户赚钱 / 留住客户 / 创造长期价值"这个终点深挖一层**，不停在表层的"省人力"。
- ⚠️ **常识性价值（如"AI 客服能省人力"）通常是对的、也是客户愿意买单的前提，但往往不是伙伴真正想强调的核心**——要读出填表背后更深的主张。

**六-B｜Key Message 必须落到"结果价值"，不能停在"感知/过程"词**
- 自检一句："这是过程中间态（如'听懂'/'识别'/'连接'），还是客户真正想要的**结果**（问题被解决 / 体验提升 / 收益增长）？"
- 过程词要**再往前推一步**到终局结果。（举例：某 AI 客服方案 KM 若写"让客户被『听懂』"——"听懂"只是中间态，要落到"听懂**并精准解决**"，甚至升维到"把每一次咨询变成一次留客机会"。此为示例，非默认。）
- 🎯 **KM 的"结果价值"必须匹配"客户案例的客群性质"，别用错动词**：写 KM 前先判断这个客群"要解决的真命题"是什么——
  - 若客群是**尚未成交的潜客/流量**：真命题是"转化 / 拉新 / 留住（防流失）"；
  - 若客群是**已付费的会员 / 长期签约客户**（人已在、钱已交，如赛马会会员）："留住"是伪命题，真命题是"**提升忠诚度 / 长期活跃 / 复购 / 放大 LTV（长期价值）**"——把一次性服务升维成"长期客户关系经营"。
  - ⚠️ 落点尽量挂到**跟钱直接相关的词**（LTV / 复购 / 增值 / 收益），比"读懂客户""服务好客户"这类感知词更打动 B 端决策者。（"读懂"是过程感知词，企业真正在意的是由此带来的留存/增值，不是客户有没有"被读懂"。）
- 🎭 **KM 一旦定稿，它的"情绪基调"必须贯穿全片，前后拍不能调性打架（每次改 KM 都要回头做一致性巡检）**：
  - KM 基调分两类——**防守/止损基调**（防流失、别让客户跑掉）vs **进攻/增长基调**（提升忠诚、撬动复购/二次增长/放大 LTV）。
  - ⚠️ 常见病：KM 升级成"进攻/增长"了，但前面开场、收窄、过渡句还在一路喊"流失/去留"，导致结尾的"增长"显得突兀、没铺垫（前面从没提过增长，结尾突然冒出来）。
  - ✅ 正确的情绪曲线 = **开场用"痛点/流失"制造紧迫（防守）→ 中段过渡句完成"从防流失到促增长"的攻守转换（枢纽）→ 结尾落到进攻/增长基调**。痛点拍讲"流失"是合理的（那是"病"，本就负向）；但**收窄拍/过渡拍要开始埋"增长/长期经营/持续创造价值"的种子**，别全程只有流失。
  - 🔑 **中段过渡句（痛点→方案之间那句）是攻守转换的枢纽**：不能只写"为了优化客户体验"（太平、只接住防守），要顺势把基调抬到 KM 的终局（如"为了让高价值客户从『用一次』变成『被长期经营、持续创造价值』"）。
  - 📋 改 KM 后的一致性巡检清单：① 开场钩子的落点词 ② 收窄拍的收口句 ③ 痛点→方案的过渡句 ④ 客户成效的价值词 ⑤ 结尾 CTA——逐一确认是否都朝 KM 的基调收敛，有"打架"的就改。

**六-C｜痛点翻译公式：功能语 → 客户后果 → business 损失**
- QA 表里填的痛点，多是**供应商视角的功能罗列**（如"海量重复咨询""知识散落各处""需支持多语言"），客户听不到"跟我有什么关系"。
- 每条痛点必走翻译公式：`供应商功能语 → 对客户造成什么后果 → 后果导致什么 business 损失`。
- **落点必须是会让企业觉得"痛"的利益点**（客户流失 / 排队久流失 / 口碑差 / 投诉 / 收益受损 / 品牌风险），不是表层现象。
- ❌ 反例（禁止直接上屏的功能语）："知识散落各处""重复咨询量大" → ✅ 翻译后："客服要现查、响应慢，客户等得久就流失，口碑受损"。
- 🚨 **落点排序：企业最 care 的是"收益/客户流失"（生产力层面），其次才是"品牌声誉/形象"（影响力层面）。** 翻译时优先往"客户流失→丢收益"上落；合规/敏感内容这类归到"品牌声誉风险"（影响力层面，重要但次于收益）。
- 🚫 **禁写企业不 care 的"内部视角"痛点**：如"人工客服工作负担重、员工累、给客服减负"——**企业老板不关心员工累不累**，只关心"由此导致响应慢→客户体验差→客户流失"。凡遇到"减负/省人力/员工效率"类表述，一律翻到"因此客户体验/流失受到什么影响"再上屏。
- 🚫 **禁写"接不接得住""扛不扛得住"这类企业不 care 的设问**：如"咨询量这么大，人工真的接得住吗？"——接得住接不住是运营内部问题，企业真正怕的是"接不住 → 客户流失 → 丢收益"。设问要落到跟钱/流失挂钩的点上。

**六-D｜开场钩子优先用"权威第三方数据"，且严禁为贴场景而泛化**
- 开场（尤其视频）优先用**权威调研机构 / 行业报告的数据**做钩子，增强真实与说服力（参考信永中和范例开场"2024 中国出海企业合规支出 488 亿"）。
- **主动上网检索**该行业该痛点的权威数据；查得到 → 按附录规范标注信源；查不到 → 标"（待补权威数据源）"，**绝不编造**。
- 🚨 **大忌：数据/表述不可为了"精准适配场景"而泛化成"正确的废话"**。写得太泛（如"高价值客户越等不起、他们贡献可观收入"）虽然挑不出错，但**毫无吸引力、不专业**。宁可用一个**具体、精准、带数字**的权威数据，也不要一句放之四海皆准的空话。
- 📐 **推荐的开场逻辑链（"先大势 → 再解释为什么 → 再聚焦案例"，环环相扣落到钱/收益）**：
  1. **趋势数据**（这个行业/技术在爆发）——如"2026 年中国智能客服市场规模预计突破 380 亿元"。
  2. **过渡句**（为什么企业愿意投？）——点出"不只降本增效，更是优化客户体验、减少等待、防止流失"，把趋势和"钱/收益"接上。
  3. **痛点数据**（不投的代价）——如"65% 消费者因等待超 3 分钟放弃咨询，年收益损失可达 10%"；再叠高价值客群的更狠数据（如"VIP 容忍度最低、等待≤15 秒否则流失""少数高价值客户贡献企业大部分收入"）。
  4. **过渡句 + 收窄到具体客户案例**——用客户官网查到的具体事实（体量/客群/规模）落地。
- ⚠️ 引用具体比例数据（如"X% 客户贡献 Y% 收入"）时，若是**行业通用结论**，只能泛化引用、**不可把具体数字套到本案例客户头上**（除非 QA/客户官网有该客户自己的数据）。

**六-E｜先"预设场景 + 提炼共性"，让引子覆盖同类企业（不止一家）**
- 落笔前两步放大受众：① **检索选定客户的业务体系**，预设其真实场景；② 把场景**提炼成一批同类企业的共性特征**，让引子"大一点"，覆盖所有有同类痛点的目标企业。
- 始终对齐**推广产品 + 目标受众**（见 Step 0）：推广的是"腾讯云×伙伴的方案"，受众是"像该客户一样有同类需求的 B 端企业"，不是只讲一家客户。
- 🧮 **mentor 会议原话总结的"可复用公式"（每次落笔前套一遍）**：`① 选一个价值词（客户体验/降本增效…）→ ② 上网查这个客户背后的服务体系长什么样（客群、体量、咨询特点）→ ③ 把它提炼成同类企业的 2-3 条共性特征（如"客户接待要求高 / 业务繁多 / 咨询频次高"）→ ④ 给共性配一个权威数据钩子（"平均等待超 X 秒客户就流失"）→ ⑤ 落到结果（流失→丢收益）`。会议原话："他以后就套着这个公式……第一步先说我提炼的是这个客户体验，第二查这个客户的客户体系什么样。"

**六-F｜能力要"重组排序成有逻辑的分层架构"，并补"双方各自价值"**
- QA 填的能力点多是**散乱、互不关联**的。不能平铺罗列，要**重组成有递进逻辑的分层架构**（典型如：简单问题层 → 复杂辅助层 → 底层合规/安全层，视方案调整）。
- 🧱 **【最重要·分层铁律】"双方能力"拍讲【企业主体实力】，"方案架构"拍才讲【产品怎么落地】——两拍严禁内容重复**：
  - 💬 **mentor 会议原话（这一层是被点名"漏掉"的必备层）**："你这个都是讲的解决方案里的功能点能帮业务实现哪些价值，但你没有写**腾讯在这里面能干啥**……所以这里面再加一层，就是**腾讯在这里面提供了什么、伙伴在这里面提供了什么**。" → 凡产出必须**显式有一层专门讲"腾讯云提供了什么 + 伙伴提供了什么"**，不能只堆方案功能点。
  - **「双方登场·能力与价值」拍** = 讲**企业主体是谁、有多强**（不点产品名怎么用）。腾讯云→"全栈技术底座 / 混元大模型 + 智能体平台 + 全球化云基础设施"这类**主体江湖地位**；伙伴→从**官网提炼可泛化到任何案例的公司实力**（团队规模、深耕行业、全生命周期交付能力）。参考信永中和范本："信永中和已在全球 23 国设 112 个办公室 / 腾讯云全球 3200+ 加速节点、60+ 可用区"——**纯主体实力白描，不提任何产品**。
  - **「方案架构·三步走」拍** = 才讲**产品怎么用**（ADP 的 RAG、Desk 的多轮、Workflow 编排等具体产品能力如何分层落地）。
  - 🚫 常见错误：把 ADP/Desk 的具体产品能力提前写进"双方能力"拍，导致和"方案架构"拍重复冗杂。**产品能力一律下沉到方案架构拍**。
  - 🔍 **伙伴主体能力必须去伙伴官网提炼**（呼应约束五第 1 类锚点）：从官网抓的是"**公司在任何案例都具备的能力**"（如"700+ 技术团队、深耕金融政企、全生命周期一站式交付"），**不是把本案例的具体动作（三语UI定制/搭这个知识库）当成公司能力**——后者太限于单一案例，不能泛化。QA 里的具体交付动作放到"方案架构"拍。
- 🔗 **过渡句禁用"强强联合"这类万金油，要直接点出"联合带来了什么价值"**：
  - 🚫 反例（空泛、无信息量）："腾讯云与悦智强强联合" / "两家都很强" / "深度携手"。
  - ✅ 正解：用"**提供从 X 到 Y 的一站式落地解决方案**"这类句式，直接说清 **1+1>2 具体是什么**（如"从 AI 技术底座到定制化落地的一站式解决方案"——一句话表明客户无需多方拼凑）。过渡句最好还能**接住上一拍的痛点、带出本方案要达成的客户价值**（如"为了让高价值客户从『用一次』变成『长期留下』"）。
- **必须补一层"腾讯云能力 + 伙伴能力 = 1+1>2"的分工价值**：谁做技术底座、谁做定制交付，各自在项目里提供了什么具体价值——原始 QA 常缺这层，要主动补齐。
- 🖋️ **架构描述要学"信永中和三步走"的具体笔力，不许写泛**：QA 填的架构常常是散乱的痛点/能力点，要拼成一个**有逻辑、有画面、够专业**的分层。写太泛会让人觉得 boring、不专业。
  - ✅ 信永中和参考笔力（可套结构）：「方案分三步走。第一步，全球基础设施一键覆盖，安全合规网络直达海外站点。第二步，多准则智能转换引擎，IFRS 与 PRCGAAP 双轨自动生成。第三步，AI 驱动票据识别与报表合并，准确率超过 99.9%。一个平台，看清所有海外子公司的财务全貌。」
  - 落地要点：每一步 = **一句能力 + 一句它解决什么**；**多看 QA 原文用其具体表述**（如"三轮上下文""可追溯源文档""Workflow 编排"等具体词），比自己造泛词专业得多；结尾用一句"一套平台/一站到底"收束整个架构。
- 💰 **"腾讯云价值"必须基于产品官网写实**（呼应约束五第 3 类锚点）：不要泛泛写"腾讯云提供技术底座"，要写清**具体是哪个产品、这个产品的什么能力、给这个场景带来什么价值**（如"ADP 的 Agentic RAG 检索引擎，保证回答准确、可追溯源文档"）。注意：这属于"方案架构"拍；"双方能力"拍只讲主体实力（见上分层铁律）。
- 🏁 **结尾/升华的落点：收口到与"钱/客户价值"挂钩的 Key Message，不空喊"适用更多场景"，也不硬凑独立的"差异化升华"拍**：
  - 🚫 反例（大家都知道、等于没说）："这套能力不只属于本客户，更多同类企业都能用" —— 常识，毫无信息量。
  - ⚠️ **"差异化升华"若与前面的"客户成效""方案架构"内容重复，就直接删掉这一拍**（实测常重复）——把差异化价值直接融进结尾 CTA 的 Key Message 收口即可，不必单开一拍。
  - ✅ 正解：结尾 CTA 直接收口到 Key Message（挂到 LTV / 增值 / 复购这类跟钱相关的终局价值），一句点睛，不铺排比。

**六-G｜旁白文风：像"陈述事实"，不像"给人上课"（学信永中和范本的克制笔力）**
> 这条最容易翻车。写视频旁白 ≠ 把"讲给同事听的逻辑口水话"直接搬上屏。信永中和范本全片零反问、零说教、句句是事实，靠**因果自然递进**推进，这才是专业营销文案。
- 🚫 **禁止把"讲逻辑的口水话"当脚本**：如"为什么企业愿意投 AI 客服？答案不只是降本增效——更是为了守住体验"——这是**说给自己/同事听、帮助理解背后逻辑的话**，不是旁白。旁白要把这层逻辑**消化后用营销语言重新包装**，直接陈述事实，不做自问自答的教学腔。
- 🚫 **禁止领导 / 说教口吻**：如"别忘了…""赶走一个，代价远超想象""要知道…"。你是在**用视频对潜在客户平等说话**，不是领导给下属划重点。
- 🚫 **反问要克制到几乎不用**：信永中和范本零反问。"仅靠人工——流失的会是谁？""人工，接得住吗？"这类反问幼稚、突兀、不 flexible。优先用**陈述句 + 事实因果**自然收口。
- 🚫 **禁止口水词 / 形容词堆砌凑气势**：如"客户等得越久走得越快""如潮水般涌来""苦心经营多年"——没有增量信息，只是在用形容词充字数。每句话都要**带信息量**（数据、事实、具体能力），删掉纯修辞。
- 🖋️ **比喻 / 金句必须贴合本方案场景，不可硬套范本**：信永中和用"账本/一笔细账"是因为它做的**就是海外财务做账**——比喻天然贴场景。换到 AI 客服场景，就**不能套"账"这类财务比喻**，要另找贴合"服务/客户/响应"的表达。范本学的是**笔法（克制、事实自证、一句点睛）**，不是**照抄它的具体比喻词**。
- 📊 **数据表述用"最具冲击力的具体形态"，别为怕越界而钝化**：如"少数客户贡献四成收入"远不如"仅占客户总量 3% 的 VIP，却贡献 40% 收入"震撼。行业通用规律**用具体数字陈述行业事实即可**（不说"本案例客户的 VIP 是 3%"就不越界），别把最猛的子弹泛化打哑。
- ✂️ **信息密度对标范本**：信永中和约 400 字讲完一个复杂方案。初稿逻辑可先铺全，但**精简阶段要向这个密度看齐**，砍解释性从句、砍修辞、留事实与能力。

## 工作流程

### Step 0｜确认输入与模式

**输入由三部分组成（缺一不可，尤其别漏第 3 步检索）：**
1. **伙伴 QA list**（一手核心输入，含多个联合方案 case + 客户案例 case）。
2. **人工筛选定 case**：由用户从 QA list 里挑一个合适的 case（**优先涉及 AI、出海场景**）及其对应客户案例。如未指定，主动请用户确认选哪个。
3. **主动上网检索权威信源**（见约束五）：围绕选定 case，检索**①伙伴官网**（方案/客户案例页）、**②客户官网**（业务场景）、**③方案涉及的腾讯云产品官网**（QA「涉及腾讯云产品」填了什么就逐个查，搞清产品能力与场景价值），补业务血肉、行业 know-how 与产品真本事。冲突时以 QA list 为准。

**再问清四件事：**
   - **产出哪个？**（PPT 故事线 / 二创视频叙事线 / 两个都要）
   - **推广的产品是什么？目标受众是谁？**（这是叙事的靶心——如"腾讯云×伙伴的某方案"，受众是"像该客户一样有同类需求的 B 端企业"。锁定后所有文案对齐这个靶心，避免只讲一家客户，见约束六-E）
   - **有无可授权客户案例？**（决定"效"的写法）
   - **本次是哪种 QA 情况？**（见下）

**QA 表的三种情况**（决定素材从哪取）：
- 1️⃣ 有联合方案 + 带授权客户案例 → 联合方案区 + 客户案例区都填了
- 2️⃣ 有联合方案 + 无/未授权案例 → 只填联合方案区，"效"走脱敏抽象
- 3️⃣ 只有单个客户案例 → 只填客户案例区

> QA 表字段 → 病/药/效 的详细映射见 `references/qa-list-mapping.md`。
> 拿到 QA 表时可顺带做一次"体检"（易填错/易误解的字段），清单见 `references/qa-list-review.md`。

### Step 1｜构建"核心故事线底座"（PPT 和视频共用）
从 QA 表提炼出这一套底座，作为两个产出物的共同根：
- **价值主张定线**（先做，见约束六-A）：AI 先判断走哪条价值主张线 + 给理由，**停下来请用户确认/补充**，再往下写。
- **Key Message**（一句话，见约束一 + 约束六-B：必须落到结果价值，不停在过程词）
- **病**：客户业务痛点（取自 QA「业务痛点」，**逐条过约束六-C 翻译公式**，翻成客户可感知的利益损失）
- **风险**：痛点的代价（若 QA 没写，从痛点合理推演，但标注"建议补充确认"）
- **药**：联合方案是什么 + 腾讯云做什么 + 伙伴做什么（**按约束六-F 重组成分层架构 + 补双方各自价值**）
- **效**：客户价值/成效（取自「整体价值」「效益」「客户收益」，按约束二/三处理）

### Step 2｜分发成 PPT 故事线
按下述**产出规格**逐页展开。详细页面结构模板见 `references/ppt-storyline-spec.md`。

### Step 3｜分发成二创视频叙事线
按病-药-效逐幕口播，~1.5分钟。详细模板见 `references/video-narrative-spec.md`。

### Step 4｜脱敏检查 + 交付
过一遍约束四清单，在对话里交付（或用户要求时写入文档）。
**交付时明确提示：这是"供与伙伴二次讨论的初稿"**，非最终定稿；并列出需伙伴确认/补充的存疑点（推演的风险、目标值、网络补充待核实处）。

## PPT 故事线产出规格（硬规则）

1. **框架 = 每页要点 + 写它的原因（背后逻辑）**——不是成稿文案，是"策划脑"级说明。给用户看到"这页放什么 + 为什么这么放"。
2. **每页必须有一句"客户视角结论"**（放标题或作为该页结论句）——讲"这对客户意味着什么价值/成效"，不是讲技术做了什么。
3. **一页一主题**——不同页讲不同方面，绝不把一个内容拆到多页注水。
4. **每页字数克制**——满屏技术堆砌是反面教材（如6T全栈页那种密度）。要点化、信息分层。

## 二创视频叙事线产出规格（硬规则）

1. **~1.5分钟**，逐幕（口播文案 + 画面/字幕提示）。
2. **病-药-效同一逻辑**，但**只抽主线、不面面俱到**。
3. **弱化"两家各做了什么"**，重心放客户价值（比 PPT 更聚焦价值）。
4. **头尾点 Key Message**，结尾**导流"下载完整联合方案"**。
5. 目的：社媒（视频号等）传播、勾起兴趣、降低理解成本。

## 关键原则速记

- 🚨 **demo≠default**：悦智/HKJC/信永中和等一切具体名都是脱敏举例，绝不设默认伙伴/客户/行业；每次以用户新给的 QA 为准。
- 视角：**客户业务视角**永远第一，技术是支撑不是主角。
- 价值主张：AI 先判断+给理由→**请用户确认**（不锁二选一，可两者兼有或全新主张）；都要往"帮客户赚钱/留客/长期价值"深挖，不停在"省人力"。
- 痛点：走**翻译公式**（功能语→客户后果→business损失），落到会让企业痛的利益点（**收益/客户流失>品牌声誉**）；供应商功能语禁直接上屏；**禁写"员工负担/减负/接得住吗"这类企业不 care 的内部视角**。
- 开场：优先用**具体、精准、带数字**的权威第三方数据做钩子（严禁为贴场景泛化成"正确的废话"）；逻辑链=趋势数据→过渡句(为什么投,落到钱)→痛点数据→收窄到客户；查不到标"（待补权威数据源）"，不编造。
- 受众放大：先检索客户业务体系预设场景 → 提炼同类企业共性，引子覆盖一类企业而非一家；对齐"推广产品+目标受众"。
- 能力：散乱能力点**重组成分层递进架构**（学信永中和"三步走"具体笔力，善用QA原文具体词，不写泛）；补"腾讯云×伙伴各自具体价值"一层（**腾讯云价值须基于产品官网写实**）；结尾收束=强调本方案**差异化价值（你有我没有的）**，不空喊"适用更多场景"。
- 统一：PPT 和视频**同一个 Key Message、同一套病药效底座**；KM 落结果价值不停在过程词。
- 输入：QA list（一手）+ 人工选 case + **主动检索权威信源**（具体案例查具体伙伴/客户官网）三段式，绝不闭门造车。
- 信源：冲突时 **QA list（一手）> 网络二手信息**；网络写进产出的内容**像论文一样附信源附录**，无法印证的标"待伙伴确认"。
- 阶段：产出是**供二次讨论的初稿**，不是最终定稿；主动标出待伙伴确认/补充处。
- 脱敏：默认保守，未授权信息一律隐去。
- 边界：只产文字故事线，不产成品；默认对话交付，不擅自改文件。
- 数据：严格依据 QA 表和素材，缺数据宁可标注"待伙伴补充"，不自行编造；分清目标值 vs 实测值。
